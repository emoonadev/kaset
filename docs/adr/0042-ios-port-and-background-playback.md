# ADR-0042: iOS port with WebView playback and background audio

## Status

Proposed (accepted once the user confirms step S0 in [`docs/ios/TRACKER.md`](../ios/TRACKER.md))

## Context

Kaset is macOS-only. This fork wants a native iOS client for YouTube Music that
keeps playing with the screen locked and keeps advancing through playlists.
The app is distributed outside the App Store (sideload / ad-hoc), so there is no
App Review constraint, but the same technical limits of iOS apply.

[ADR-0001](0001-webview-playback.md) established that playback must go through a
`WKWebView`: DRM-protected content and bot detection rule out native streaming.
The open question was whether a `WKWebView` can keep playing, and keep advancing
the queue, on iOS while the app is in the background.

A throwaway spike (one `WKWebView` on `music.youtube.com`, `AVAudioSession(.playback)`,
`UIBackgroundModes=audio`, heavy logging) was run on a physical iPhone. Evidence is
summarised in [`docs/ios/spike-findings.md`](../ios/spike-findings.md).

## Decision

1. **Playback stays in a hidden 1×1 `WKWebView`**, exactly as on macOS. No native
   stream extraction, no `AVPlayer` for music.
2. **Background audio uses `AVAudioSession(.playback)` + `UIBackgroundModes=audio`.**
3. **Keep the WebContent process alive while paused** with an inaudible Web Audio
   graph (`AudioContext` + oscillator through a near-zero gain). Without it iOS
   freezes the page shortly after a pause and lock-screen play no longer reaches it.
4. **Lock-screen next/previous come from `navigator.mediaSession` handlers** installed
   by the injected script (and `seekforward`/`seekbackward` cleared). Native
   `MPRemoteCommandCenter` registrations are overwritten by WebKit and are not used
   for transport commands.
5. **Sign-in uses a Mobile Safari user agent.** Google rejects embedded sign-in with
   a desktop macOS user agent on an iOS platform ("Something went wrong"). Playback
   keeps the existing desktop user agent.
6. **Code sharing is "shared sources", not a module split.** A new Xcode iOS target
   (generated by XcodeGen from `iOS/project.yml`) compiles `Sources/Kaset/{Models,Services,ViewModels,Utilities}`
   in place, minus an explicit exclude list that is burned down step by step. iOS-only
   code lives in `Sources/KasetiOS/`. macOS code is only touched with `#if os(macOS)`
   / `PlatformImage`-style typealiases; no files are moved.
7. **The iOS UI is new and native** (SwiftUI, tab bar, mini player, now-playing sheet).
   The macOS views are not ported.

## Consequences

### Positive

- The decisive risk (background playback) is retired before any UI work.
- macOS behaviour and upstream merges are barely affected: SwiftPM target and file
  layout are unchanged; the exclude list makes remaining work measurable.
- Playback, queue, identity and recovery logic (≈18k lines in `Services/Player`)
  is reused rather than re-implemented.

### Negative

- A permanently-running `AudioContext` costs battery. It has not been measured yet
  (step S13).
- iOS may still terminate the WebContent process under memory pressure; recovery
  needs explicit handling (step S13).
- The shared-source target compiles with a long exclude list at first, which is
  noisy until the burn-down finishes.
- `Sources/Kaset/Views/MiniPlayerWebView.swift` mixes the platform-independent
  `SingletonPlayerWebView` with an `NSViewRepresentable`; it needs `#if os(macOS)`
  guards (step S4).

### Not decided here

- Whether the native `NowPlayingManager` or page-level Media Session owns lock-screen
  metadata on iOS. The spike proved the page-level route; the native route is untested
  (step S11 decides with evidence).
- iPad layout, CarPlay (needs an Apple entitlement), YouTube video mode.
